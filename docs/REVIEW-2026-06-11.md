# Architecture & Logic Review — 11 June 2026

Scope: grading pipeline, problem creation, capture engine, auth. UI untouched. All changes are uncommitted — review and commit what you accept.

## Overall assessment

The architecture is sound and the problem-solving approach makes sense:

- **Grading model** — NRMSE against a golden waveform for analog, exact cycle-match for digital, topic-based thresholds. This is a reasonable, defensible grading strategy for a LeetCode-style circuit platform.
- **Three-test suite** (no-load / max-load / min-load) is a genuinely good idea: it forces solutions to be robust, not just curve-fit to one operating point.
- **Server-side grading** (`/api/grade`) was the right structural move; the route is well organized.
- **Capture engine** (`samplingUtils`) — discovery-by-convention (voltmeter, `input`/`clk`/`OutputN` labels) is pragmatic and works, but it is implicit contract; documenting the labeling convention for creators is essential (see prod notes).
- **Separation** of `gradingUtils` / `signalUtils` / `samplingUtils` is clean and all are unit-tested (63 tests, all passing).

## Issues found and fixed in this pass

### 1. Grading trusted client-supplied parameters (integrity — most important)
`/api/grade` read `topics`, `testType`, and `testbench` from the request body. A user could:
- send `topics: ["Power Electronics"]` to get a 30% error threshold instead of 5%;
- send `testType: "signal"` on a load problem so only test1 was required for completion.

**Fix:** the route now fetches the problem document server-side and derives `testType`, `topics`, and `testbench` from it. The client sends only `problemId`, `testKey`, `capturedData`. `AutoMarker.jsx` updated to match.

### 2. Short-capture pass exploit
NRMSE compared over `min(user.length, expected.length)` — submitting a handful of samples matching the start of the solution would pass. **Fix:** the route rejects captures shorter than the solution, and caps payload sizes (200k analog samples / 10k digital rows) so hostile payloads can't burn CPU.

### 3. `sampleCount` was silently ignored everywhere
`Simulator.jsx` called `captureAnalog(sim, 30720)` — but the function expects an options object, so the number was discarded and the default always used. Both creator capture and solver capture were affected (consistently, so grading still worked — by accident). **Fix:** pass `{ numSamples }` properly.

### 4. Sample-rate mismatch was never checked
Sample-by-sample comparison is meaningless if the solver's sim runs at a different time step than the solution capture. **Fix (two halves):**
- Creation now stores the sample rate the capture **actually ran at** (`capturedData.sampleRate`) instead of the form's `timeStep` field, which could silently disagree with the simulator.
- Grading rejects submissions whose capture rate drifts >5% from the stored solution rate, with an actionable message ("reset the template").
- *Caveat:* problems published before this change store the form-derived rate; if a legacy problem's form value didn't match its real sim dt, graders may now get the mismatch error. Republishing the problem fixes it.

### 5. Non-atomic publish could create broken problems
Publishing did `addDoc` + up to 4 sequential `setDoc`s. A failure halfway left a problem with no solution docs — exactly the case that 500s at grade time. **Fix:** single `writeBatch` — all docs commit or none do. Also: empty captures are rejected at capture time, load resistances validated > 0, `sampleCount` stored as a number.

### 6. Digital grading had no missing-solution guard
A missing/malformed digital solution doc parsed to `[{decimalOutput: NaN}]` and graded against garbage. **Fix:** parse with `Number.isFinite` filter + same explicit guard the analog path has.

### 7. Captures could hang forever
If the sim was paused, never converged, or had no clock edges, `captureAnalog`/`captureDigital` promises never settled — UI stuck on "Analyzing…" with no way out except reload. **Fix:** 60s timeout that detaches the handler, stops the sim, and rejects with a useful message.

### 8. Forgeable auth fallback could run in production
Without the Admin SDK, the route decoded ID tokens **without signature verification**. Fine for dev; in prod a missing env var would mean trusting forged uids. **Fix:** the unverified fallback is now dev-only; in production without Admin SDK all requests are treated as anonymous.

### 9. Rate limiting skipped anonymous users
Only authenticated users were limited; anonymous requests could hammer grading + Firestore reads freely. **Fix:** anonymous requests are limited per-IP; the limiter map now self-prunes.

### 10. `syncUserDocument` reset account state
The merge wrote `role: "user"`, `totalPoints: 0`, `completedProblems: []` on every call — calling it on an existing creator would demote them and wipe progress. Currently only reachable on first login, but one refactor away from a nasty bug. **Fix:** identity fields always merge; account-state defaults are written only when the doc doesn't exist.

### 11. Solutions tab was dead
`SampleSolution` reads `problem.solutions`, but the solve page never fetched the `solutionWaveform` subcollection — the tab always rendered blank. **Fix:** the page now fetches it in the same `Promise.all`. (Note this confirms solutions are *intentionally public*, which matters for the prod discussion below.)

## Deliberately not changed

- **Digital cycle count hardcoded at 330** (`Simulator.jsx`). Wiring it to `sampleCount` would make existing digital problems (default 30720) capture 30720 cycles. Decide the semantics first: either a separate `cycleCount` field, or `sampleCount` means cycles for digital problems with a sane default.
- **M3 (sampleRate location)** — you held it. The new per-test stored rate makes it less urgent, but problem-level metadata still belongs on the problem doc long-term.
- **Grading-failure UX in `AutoMarker`** — errors only go to `console.error`; the user sees the spinner end with no explanation. Fixing means UI work, so it's left for you.
- **`getVerdict` digital thresholds** — the 0.05 entries for digital topics in the thresholds map are dead config (digital requires 100% match). Harmless; clean up when convenient.

## Prod-readiness roadmap (the next phase)

In rough priority order:

1. **The fundamental anti-cheat gap: submissions are waveforms, not circuits.** The server grades whatever samples the client sends — and the golden waveform is publicly readable (Solutions tab + open Firestore rules), so anyone can POST the solution back and pass. Server-side validation can only get you so far while the *simulation* runs client-side. The real fix is storing the user's exported circuit with each passing submission, then (a) at minimum spot-check/replay suspicious ones, (b) ideally re-simulate server-side (CircuitJS headless in Node) before marking complete. Decide how much you care for v1 — for a learning platform, "cheaters only cheat themselves" may be acceptable; for rankings/competitive features it isn't.
2. **Firestore rules hardening.** Rules in the repo aren't necessarily what's deployed — verify. `UserProgress` client `create/update` rules still allow a user to write their own progress doc directly, bypassing grading. Now that the API owns that write via Admin SDK, lock client writes to `UserProgress` entirely.
3. **Deploy config:** `FIREBASE_SERVICE_ACCOUNT_JSON` must be set in prod (route now refuses unverified tokens without it, so missing config = nobody's progress saves). Add a startup assertion or health endpoint.
4. **Rate limiter is in-memory** — fine for single instance, swap for Redis/Upstash if you scale horizontally or deploy on serverless (each lambda gets its own map, limits become ineffective).
5. **Firestore cost control:** solution waveforms are ~30k-line strings fetched on every problem view and every grade. Consider downsampling what the Solutions tab fetches, caching solutions in the API route (per-instance LRU), and Firestore doc-size limits (1 MiB) if sampleCount grows.
6. **Creator conventions doc:** voltmeter required, `input`/`clk`/`InputN`/`OutputN` labels, timestep discipline. Most "problem doesn't grade" support tickets will trace to this.
7. **Monitoring:** structured logs around grade verdicts and 4xx/5xx counts; you currently have no visibility into how often grading fails and why.
8. **Tests for the API route** itself (the grading utils are tested; the route's validation/authority logic isn't — vitest + mocked Firestore would cover the cheat paths fixed today).
